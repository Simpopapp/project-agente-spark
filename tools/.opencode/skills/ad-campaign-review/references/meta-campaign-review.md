# Meta campaign review

Overlap: SKILL.md owns the review contract, the attribution rules, and the report shape; this file owns the Meta reads and the Meta mechanics that instantiate them. Every call goes through `meta_ads--request`, never `standard_connectors--call_gateway_connection`. The review is read-only: GET only, no POST, and no approval card is involved.

## Read the evidence

Tracking state comes before conversions, so the ad-set and pixel reads precede insights.

1. `GET /v26.0/act_<id>?fields=currency,account_status,funding_source_details,timezone_name`. Report account blockers — account status and funding state — without inventing one. Every money figure is in the returned currency; say which. `timezone_name` is the account's own time zone, which every reporting date depends on: Meta resolves an insights `time_range` as local calendar days there, never in UTC, so read it as part of this step rather than as an extra call.
2. `GET /v26.0/act_<id>/campaigns?fields=name,objective,status,effective_status,advantage_state`. Record delivery state per campaign. `effective_status` carries why a campaign is not delivering; for a rejection read the ad's `effective_status` and `ad_review_feedback`.
3. `GET /v26.0/act_<id>/adsets?fields=name,campaign_id,status,effective_status,optimization_goal,promoted_object`. Both fields live on the ad set, not the campaign. `optimization_goal` is what the ad set actually buys, and it decides which result to judge it on: `OFFSITE_CONVERSIONS` buys conversion count, `VALUE` buys conversion value, `LINK_CLICKS` and `LANDING_PAGE_VIEWS` buy traffic, `REACH` and `IMPRESSIONS` buy awareness, and app, catalog, and engagement goals each buy their own thing. Judge every ad set against its own goal — a traffic ad set with no conversions is working as configured, not underperforming. Externally created campaigns reach goals Lovable never creates, so treat an unfamiliar goal as its own yardstick rather than forcing it onto a conversion one. `promoted_object` separately carries whatever object the goal points at; read it, never infer the goal from it.
4. Whenever an ad set's `promoted_object` carries a `pixel_id`, check that pixel: `GET /v26.0/<pixel-id>/stats?aggregation=event`. Key this on the field being present, never on a list of goal names — `VALUE` carries a pixel just as `OFFSITE_CONVERSIONS` does, and an unfamiliar goal carrying a `pixel_id` still has a pixel worth checking. Only where no ad set exposes a `pixel_id` is there no pixel behind the campaign, and that absence is not a tracking finding. Stats reports what has already fired, so an event no visitor has triggered yet reads as missing: absent stats is not a broken pixel, and unavailable history stays unknown.
5. `GET /v26.0/<campaign-id>/insights?time_range={'since':'<first-day>','until':'<last-day>'}&fields=impressions,reach,clicks,spend,actions,cost_per_action_type`, both bounds being the review window's local dates in the step 1 time zone. A `date_preset` only reaches Meta's fixed windows, so it cannot serve a user-requested window or the 30 complete days the review defaults to. Conversions appear in `actions` and cost per result in `cost_per_action_type`, both keyed by action type — name which action type a reported number counts, and pick it from the goal step 3 reported: the `custom_event_type` from `promoted_object` where the goal buys conversions, clicks or landing page views for a traffic one, `impressions` or `reach` for an awareness one. Report a campaign-level number as a campaign-level number. `cost_per_action_type` here divides the whole campaign's spend by each action type's count, so it is a cost per result only where step 3 shows every ad set in that campaign buying the same result: the same `optimization_goal`, and the same `custom_event_type` where the goal carries one — a traffic campaign whose ad sets all optimize `LINK_CLICKS` qualifies on the goal alone, since that goal has no event. Any difference in what the ad sets buy, including two conversion ad sets on different events, means the figure charges all the spend to each action type and must not be presented as a cost per result. To judge an ad set, or a campaign whose ad sets differ in either, read the same insights edge on the ad-set id — `GET /v26.0/<adset-id>/insights` with the same fields. Without that read, keep every conclusion at campaign level and say plainly that per-ad-set performance was not established. Never present a conversion count as the result of a campaign that does not buy conversions. These fields carry counts and cost per count, never conversion value or return on ad spend, so a `VALUE` ad set is reported on delivery, spend, and conversion counts with value and ROAS named as unavailable from this read — never with a count substituted for the value it was optimizing toward. State that `time_range` as the reporting window, and compare only figures sharing it.
6. A daily series — charting the window's shape in a requested report — means the same insights edge on the account with `time_increment=1`: `GET /v26.0/act_<id>/insights?time_increment=1&time_range={'since':'<first-day>','until':'<last-day>'}&fields=spend,impressions,clicks`, which returns one row per date for the whole account. Its bounds are the same local dates step 5 uses, so it waits on step 1's `timezone_name` even though it needs no id. Reading it on a campaign or ad-set id instead returns a series per object, and `level=campaign` multiplies the rows the same way; both page rather than truncate, so a long window arrives across `paging.next` pages that must all be followed before the series is complete. Dates with no delivery return no row, so a gap is an unserved day rather than a missing read.

## Deeper evidence reads

These extend the evidence reads whenever the answer needs more than the briefing establishes, in chat and in a requested HTML report alike; the skill's diagnosis section owns the analysis. Supply query parameters through `meta_ads--request`'s `query_params`, not inside its `path`.

1. Include `attribution_spec` in the ad-set read. For detailed conversion reporting, use ad-set insights with `use_unified_attribution_setting=true` and the same explicit `time_range` for every read, so results follow each ad set's attribution setting. Keep different settings separate; an unavailable setting stays unknown rather than being labelled seven-day click.
2. Add `inline_link_clicks` to the insights fields for destination-click analysis. Landing-page views and conversion events come from `actions`, keyed by `action_type`; use the returned action names rather than the flattened fields of a third-party connector. `clicks` counts all clicks, so it cannot stand in for link clicks. Overlapping purchase or registration action types are alternatives, not counts to sum.
3. For a warranted creative drill-down, read `GET /v26.0/<campaign-id>/ads` with `fields=name,adset_id,status,effective_status,creative`, then the campaign's insights with `level=ad` and fields `ad_id,ad_name,adset_id,spend,impressions,inline_link_clicks,actions,cost_per_action_type`, using the same attribution setting parameter and window as step 1. Join by ad id, retaining enabled ads absent from a complete insights result as no delivery; a failed or partial read is unknown, not zero. Follow pagination through `meta_ads--request` using the returned cursor, not credential-bearing paging URLs. Results belong to the ad, not an individual asset inside a dynamic creative.

## Meta specifics for the attribution rules

* Group steps 1, 2, and 3 into one `meta_ads--request` call: they address `act_<id>` and depend on nothing an earlier response carries. Steps 4, 5, and 6 each do depend on one — the pixel id, the campaign ids, and the step 1 time zone the two windowed reads date their `time_range` in — so they go in follow-up calls. One call composes every operation in it before Meta answers any of them, and a `$N.id` reference resolves only against an earlier create in the same call, which a review never makes; batching a dependent read early does not fail loudly, it just sends the wrong window or a rejected chain.
* Relay a Graph error's `error.message` near verbatim, minus raw ids or URLs. On a rate-limit or temporary-error code wait a minute and retry once; on any other persistent 4xx fix the request rather than retrying.
* A campaign's brief file records its settled intent: read it for what the campaign was meant to do before judging whether it is doing it. Live ids, budgets, and statuses come from the reads above, never from the brief.
* Meta reports `reach` alongside impressions, so the "few impressions" branch can distinguish narrow reach from low frequency.
* Pixel stats establish event receipt, not browser/CAPI deduplication or consent. Where both sources report the same outcome, inspect their shared `event_name` and `event_id`; use Events Manager's diagnostics and Test Events when available, without treating test receipt as attributed results. Meta has no equivalent to Google's denied Consent Mode pings; a blocked consent route has reduced event coverage, and CAPI `opt_out` or Limited Data Use does not supply consent.
* `use_unified_attribution_setting=true` changes the basis: step 5 answers on Meta's default attribution, a read carrying the parameter on each ad set's own setting. Re-read campaign-level figures with the same parameter and window before comparing, and name the setting a restated number follows.

## When the user asks to apply a fix

Changes go through the normal Meta management path, one change at a time. Pause, resume, rename, and budget changes are `POST /v26.0/<object-id>` with the changed field, each showing an approval card the user's approval of carries the spend decision. Creatives are immutable: changing a live ad's copy or image means creating a new creative and pointing the ad at it. None of that happens during the review.
